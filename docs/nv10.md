# The NV1x: the Quadro2 MXR (GeForce2 MX class)

**Status (2026-11-27): the Quadro2 plan's Q1 and Q3 done, Q4 under way. The TNT2 layer drives the NV11 (2D byte for
byte the software model's). The NV1x's own 3D class, Celsius (0x96), draws from DOS exactly as Mesa's NV11 driver
drew under nouveau. DOS-GL has a back end on Celsius (`gl/src/backend/nv10`). The D3D5/D3D6 classes (0x94/0x95) draw
nothing yet.**

The plan is the owner's of 2026-11-26 (Q0-Q6: the NV1x in the TNT2 layer; the TNT2 back ends on 0x94/0x95; Celsius's
bring-up with nouveau's reference; DOS-GL's Celsius back end; hardware T&L; docs). The owner chose "Celsius next,
0x95 later" on 2026-11-27, after 0x95 drew nothing.

## The card

- **Bench E** (Tualatin P3-S, i815; GLOS on its Windows 98 partition, Ubuntu beside it): a Quadro2 MXR, PCI
  `10de:0113` revision b2. `PMC_BOOT_0` = `011300b2`. 32 MB (`PFB` `0x10020C` = `02000000`), core PLL 175 MHz,
  memory PLL 166 MHz.
- **Classes** (nouveau's `gr/nv15.c`, envytools): 2D 0x4a, 0x52, 0x5f/0x9f, 0x62 (surfaces, in place of the TNT2's
  0x42), 0x89, 0x8a; 3D 0x93 (surfaces), 0x94/0x95 (the TNT's 0x54/0x55, method for method), 0x96 Celsius.
- **References and their licences:** xf86-video-nv 2.1.23, Mesa 20.3.5's classic nouveau NV1x driver, Linux 6.6's
  nouveau (MIT files only), envytools' rnndb and hwtest (MIT). All in `~/bench-archive/nv10-src/` with their URLs,
  hashes and licences. GPL code is read for facts only.

## Safety rules (from the references; kept on the card)

- Never write CR44, CR2E or CR1F, 0x600860, the DAC or the pixel PLLs: NV11 lock-ups. No palette reads: an unused
  head's PLL can hold garbage that locks the chip. Head A only; modes and pitch by VBE (4F02, 4F06).
- The cursor and CRTC pitch writes are refused on NV1x (`tnt2_set_pitch` returns -1; the device's caps say no
  cursor).

## Q1: the TNT2 layer on the NV1x (bench E, 2026-11-26)

- **The instance memory (PRAMIN) is reversed over the top 512 KB:** instance offset X is video memory's
  `size - 16 - X` (NPRAMIN: 0x20000 at `01fdfff0`, 0x7fff0 at `01f80000`). The TNT2's layout (its ring at `size -
  128 KB`, the image scratch after it) would put the scratch on the NV11's hash table and objects. On NV1x everything
  stays below `size - 512 KB`: `fb_usable` = `size - 640 KB`.
- PGRAPH's NV10 set-up after xf86-video-nv's `nv_hw.c` (tile regions copied to 0x400B00, 0x400144, 0x400714, the
  debug registers, the limits); nouveau's pipe defaults through 0x400F50/54; 2D surfaces by class 0x62; DMA objects
  for video memory by class 0x3D (handle `0x8000001B`, RAMHT slot 11).
- NTWOD is byte-exact at 8, 16 and 32 bits except mono expansion at 32 (the chip sets the top byte); RGDEV passes.

## Q3: Celsius from DOS (bench E, 2026-11-27)

- **Mesa's set-up, captured:** on bench E's Ubuntu (X, Mesa 18.0.5's `nouveau_vieux`; the packages listed in
  `~/bench-archive/bench-e-captures/packages-to-install.txt`, to be removed when the Celsius work ends) an
  `LD_PRELOAD` on the pushbuffer ioctl recorded Mesa's command streams for eleven scenes; Mesa's initialisation is 273
  method/value pairs, now a table in the layer (`tnt2_celsius_init`). Every DMA handle points at the 0x3D
  video-memory object.
- **The object's word 0 needs bit 22 ("new"):** `0x01400096`. Without it a Z16 render target traps (PGRAPH_INTR
  bit 20 on method 0x208); only Z24S8 is allowed (envytools' hwtest `MthdSurf3DFormat`).
- **Render targets:** RT_FORMAT `0x113` (R5G6B5 with Z16, linear) and `0x105` (X8R8G8B8 with Z24S8) both draw. Six
  no-ops before a target change (Mesa: "nv11 seems to get sad").
- **Drawing** as Mesa's software-transform path: VIEWPORT_TRANSLATE (0x6E8) = the viewport's centre less 2048; the
  projection (0x500, row-major) the viewport's scale alone; VTXBUF_FMT(i) (0xD04 + 8i) = stride << 8 | fields << 4 |
  type; VTXBUF_OFFSET(i); VALIDATE (0xCF0); BEGIN (0x13FC) = primitive + 1; BATCH (0x1400) = (count - 1) << 24 |
  first; END.
- **A position with w** needs VTXBUF_FMT's homogeneous bit 24 (`0x01000000`); four fields without it trap.
- **Textures** as Mesa's: TEX_FORMAT (0x220) = DMA 0 | 5 << 4 | 1 << 12 | format (A8R8G8B8 0x300, R5G6B5 0x280,
  A1R5G5B5 0x100, A4R4G4B4 0x200) | log2 width << 16 | log2 height << 20 | wraps << 24, << 28 (repeat 1, clamp to
  the edge 3) | MIPMAP 0x8000; TEX_ENABLE (0x228) 0x40000000 with the last level at bits 14-17; TEX_FILTER (0x248)
  mag << 28 | min << 24. The TNT2's swizzle is Celsius's (DCEL1's checker exact).
- DCEL0 (a Gouraud triangle) and DCEL1 (a textured quad; Z16 LESS) match their models pixel for pixel.

## Q4: fog, measured (DCFOG, bench E, 2026-11-27)

With the transform not bypassed (0x3E8 = 6, Mesa's) and FOG_COORD (0x2A0) 0, the vertex's own fog value c (vertex
slot 7, which is the secondary colour's alpha) and FOG_COEFF k0..k2 (0x680) give v = k0 + k1 c + k2 c²; then
FOG_MODE (0x29C):

| Mode | f | GL's coefficients (d the eye distance) |
|---|---|---|
| linear, 0x2601 | v - 1 | k0 = 2 + start / (end - start), k1 = -1 / (end - start) (Mesa's) |
| exp, 0x800 | 2^(16v - 24) | k0 = 1.5, k1 = -0.0901684 density (log2 e / 16) |
| exp with \|c\|, 0x802 | 2^-\|16v - 24\| | as exp |
| exp2, 0x803 | 2^(-(16v - 24)² / 8) | k0 = 1.5, k1 = -0.2123305 density (√(8 log2 e) / 16) |

Each within one step of 8 bits of the model across its range. Mesa's 0.09 and 0.21 round these. **exp and exp2 are
applied to each pixel's interpolated value, and fog and colours interpolate in perspective**: a vertex's eye-space
distance (affine in eye space) gives GL's per-fragment fog in every mode, with no triangle splitting.

## Q4: DOS-GL's back end on Celsius (`gl/src/backend/nv10`)

- Chosen when the TNT2 device finds an NV1x (`DGL_NV_CLASS=95` keeps the TNT2's back end).
- GL transforms and clips on the CPU, as for the other cards. The vertices go into a 256 KB area in video memory, in
  clip space (x, y, z, w; colour B8G8R8A8; two texture coordinates; the eye distance), fenced a quarter at a time,
  drawn as triangle lists. The chip divides.
- **The guard band is wide** (DCGUARD, bench E): a screen-covering triangle whose corners lie up to 10,000 pixels
  off the screen draws every pixel with its colours exact, at w 1 and 4, either way round. The clipper's x and y
  planes are 8,000 pixels from the viewport's centre; near and far are clipped exactly.
- **A vector method is taken when its last word is written.** FOG_COEFF's three, the projection's sixteen, the
  viewport translation's four: a cache that skipped an unchanged last word (k2 = 0 for every fog mode) left the chip
  with the previous mode's coefficients (t10: exp drawn with linear's). The back end sends such a vector whole when
  any of it changed.
- **VTXBUF_VALIDATE before every draw:** the vertex fetch keeps video memory's lines, and a draw's first vertices
  often share a line with the previous draw's end, fetched before the CPU wrote them (conformance t16, t18, t27,
  t29, t31, t32 drew triangles from stale vertices without it). It costs nothing measurable (DCPERF: 45 us for a
  thousand). The texture cache, by contrast, saw texels the CPU rewrote with the chip idle every time (DCTEXC).
- DOT3_RGBA: a general combiner's alpha portion has no dot product, but the colour portion's result is in all three
  channels; with the second combiner free it copies spare0's blue (the alpha portion's "RGB" usage) into the alpha.
- Culling by the sign of the clip-space triangle's determinant (no division); polygon offset by the chip.
- The texture environments on the register combiners after Mesa's `nv10_state_frag.c` (MIT); fog on the final
  combiner (A the fog factor, C the fog colour).
- **Speed (bench E, GLQuake's timedemo demo1 at 640x480, -mtex):** 19 fps at first, the chip the bottleneck (the
  swap's wait 400-800 ms a second; 69 fps at 320x240). DCPERF showed draws and state changes cheap (3,000 small
  triangles: 1.6 ms as one draw or as 1,000); DCFILL showed every pixel slow, worst with the depth test or
  blending (19-32 Mpixels/s). **The cause: PGRAPH's DEBUG_2 as xf86-video-nv sets it (0x24E00810). nouveau's
  0x25F92AD9** gives untextured 346 Mpixels/s (two a clock at 175 MHz), textured 258, the depth test LESS 169,
  blending 184; GLQuake 19 -> 65 fps. nouveau's DEBUG_3 (0xF5DE0830) traps the layer's 2D rectangle object and is not
  used. Tiling the colour and depth buffers (PFB tile regions, pitch 1,280) changed nothing measurable. A second
  texture halves the fill rate (116 Mpixels/s; the second combiner alone costs a third: 175); write-combining the
  frame buffer (GLOS's `MTRR LFB ON`; the card isn't on GLOS's automatic list) adds 8% (65 -> 70 fps).
- **The memory bus is not the limit it first seemed.** xf86-video-nv reads a 64-bit bus from PEXTDEV 0x101000 bit
  4 (clear here), but DCFILL's untextured fills disprove it on this card: the depth test LESS with writes at 16
  bits (6 bytes a pixel) ran at 306 Mpixels/s, about 1.84 GB/s, beyond 64-bit SDR's 1.33 GB/s at 166 MHz; so
  the bus is 128-bit, as the Quadro2 MXR's specification says, and that strap means something else on the NV11.
  At 32 bits: flat 333, blending 162, the depth test 129 Mpixels/s (1.3-1.5 GB/s). nouveau on the same card
  (Mesa 18's nv11, 32-bit X) was no faster than DOS-GL (two textures 74 Mpixels/s, the depth test 91, blending 87;
  ~/bench-archive's glfill.c); NREGS against its registers: it tiles its buffers, DEBUG_3 0xF5DE0830, PFB 0x100210
  0x80003C3C (the BIOS's 0x8000FAFA). A second texture costs more than memory explains (115 against 258).
- **Clocks: core 175 MHz, memory 166 MHz, as the board's own BIOS sets them.** The BIOS (C000's image: "IA Quadro2 EX
  VGA BIOS", MSI, 3.11.01.26.14 of 08/29/01; kept private in ~/bench-archive) sets 100/83 MHz first (INIT_PLL,
  opcode 0x79), then picks both from 16-entry tables by a board strap (CRTC 0x3C bits 7:4; INIT_IO_RESTRICT_PLL,
  opcode 0x34, nouveau's decoding): core 175 175 120x7 143 150 150 200 120 200 143, memory 166 166 120x6 140 166 143
  143 166 150 166 183 (MHz). The PLLs read 175/166: entries 0-1. A Quadro2 MXR is specified at 200/183; this board's
  BIOS calls it a Quadro2 EX, and pairs 200 MHz only with 166 memory. nouveau leaves them as the BIOS set them.
  The board's parts (read by the owner): the GPU marked Quadro2 MXR (rated 200 MHz), the memory Winbond
  W986432DH-6, 2M x 32 SDRAM rated 166 MHz: four of them, a 128-bit SDR bus, already at its rating. The clocks stay
  as the BIOS sets them (the owner, 2026-11-27).
- **Conformance on bench E (2026-11-27, 16 bits):** all 44 tests pass or skip as the manifest allows (t33 stencil
  and t34 lines: the software renderer's only; t36 LOD bias, t37 anisotropy, t42 cube maps: not offered yet).
  t10 and t44 (fog in all three modes) pass with no pixel beyond the tolerance: per-fragment fog with no splitting.
  At 32 bits (`DGL_COLOR_BITS=32`: X8R8G8B8, Z24S8) the same.

## Q5: hardware transform and lighting on Celsius (bench E, 2026-11-27)

- **What the chip takes** (DCTNL against the CPU's path): PROJECTION transforms the object position directly
  (viewport x P x MV); MODELVIEW only gives eye space (fog, lighting, eye-linear generation); the chip clips at the
  near plane itself and culls by GL's winding (CULL_FACE and FRONT_FACE take GL's enums). Fog from MODELVIEW
  (FOG_COORD 3) is identical to the CPU path's eye distances. Primitives are GL's own (+1); indices 16-bit, two a
  word (VTXBUF_ELEMENT_U16).
- **The back end** sends draws from the arrays (glBegin's with DGL_TNL_IMM) to the chip's transform when it can do
  their state: lighting (not two-sided), fog, generation (s and t: object, eye linear, sphere map), texture
  matrices; user clip planes and two-sided lighting stay on the CPU's path. Static buffer objects' vertices are kept
  converted in video memory (the Radeon back end's X3b cache) and drawn by indices; lit draws carry their normals in
  an array of their own (slot 5). GL_DGL_hw_tnl is reported; DGL_TNL=0 turns it off.
- **Lighting** after Mesa's nv10_state_tnl.c, its fitted spot and shininess coefficients included: t40 within
  conformance's tolerance. LIGHT_HALF_VECTOR and LIGHT_ATTENUATION write the same word of the chip's light (envytools'
  hwtest), so a cache of sent values must not skip either. With LIGHT_MODEL bit 1 clear, specular goes into the
  primary colour.
- **Measured** (bench E): conformance 44/44 by default and with every eligible draw forced to the engine; DLIT (a lit
  colour-material terrain from a buffer object) 344.5 fps on the chip against 29.5 lit by the CPU; DVBO (Fifth
  Wheel's chunks, fogged) 61.5 against 12.6; DTGEN's frame within 9 levels of the CPU's (32 of 921,600 components
  beyond 3); DFOG2's factors GL's within a 6-bit step, depending on eye depth alone.

## Open

- 0x94/0x95 draw nothing (no trap) after three fixes; Glide's path waits for them (the owner: "0x95 later").
- LOD bias (TEX_FILTER bits 8+), anisotropy (TEX_ENABLE bits 4-5) and cube maps (TEX_FORMAT bit 2): measured
  before they're offered. Stencil at 32 bits (Z24S8) is wired but untested: t33 runs on the software renderer only.
- The T&L code the Radeon and Celsius back ends share, moved into one file (gl/src/backend/tnl.c), with the 7500
  proven unchanged on the P3 (the owner chose Celsius first, then the extraction).
