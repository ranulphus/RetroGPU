# B2: the software renderer, a plan

**Status (2026-11-14): v1, approved by the owner ("Approve, start B2"); under way.** The owner's answers: scanline
spans; testing as below (correctness natively on the host against OSMesa, a short 86Box smoke only from B3, speed on
bench-g400's Pentium II and bench C's 486 for the floors, the P4 bench later for the whole matrix). Step B2 of the software renderer's plan
(`docs/backends.md`), on B1's two levels (`docs/b1.md`). Built by the DOS-GL session (the owner, 2026-11-13).
B1 and the ViRGE/DX's device (`docs/virge.md` V3) are on main. Steps B2.0 to B2.7 are done on branch `b2` (local);
see "Where it stands" below.

## What B2 is, and is not

B2 is a rasteriser that draws GL 1.1 into memory, behind GL's back-end interface, tested on the host against
OSMesa. It covers everything `docs/backends.md` lists for it:
- **Rasterising:** triangles, lines and points, perspective-correct.
- **Textures:** nearest, bilinear, mipmaps, the four GL 1.1 environments, two texture units.
- **Per pixel:** depth, alpha test, blending, fog, scissor, the colour mask, and 8-bit stencil.
- **Colour:** 16, 32 and 8 bits (a fixed palette).
- **Speed:** MMX loops beside plain ones.

Where the pixels are shown is B3 (a VBE framebuffer, a GLOS window), and so is `dglInit` taking the software
renderer on a PC without a Matrox card. The tests in their three tiers are B4. B2 starts B4's first tier (the host,
against OSMesa), because a rasteriser cannot be built without it.

## The parts, and where they live

- **The core** (`hal/src/soft/`, header `hal/include/soft/soft.h`): screen-space triangles, lines and points
  with their attributes, drawn into a colour buffer, a depth buffer and a stencil buffer by a pipeline state.
  - **It knows no GL.** Its state is what GL's environments and Glide's combiners both reduce to (the owner's
    answer of 2026-11-09: one core for GL and Glide): texture stages, blend factors, fog (by a table, as Glide's
    is, or by factor), chroma key, W or Z depth.
  - **At the device level, beside the HAL,** because Glide (and GLOS's desktop) will use it too.
  - **Built for every target:** DJGPP, the host, 32-bit Linux.
- **GL's software back end** (`gl/src/backend/soft/`): `dgl_backend` in software. It does:
  - GL's state turned into the core's state;
  - clipping (the shared `dgl_clip_polygon`, with no guard band) and projection to the core's sub-pixel fixed
    point;
  - polygon modes, culling and polygon offset;
  - textures turned into the core's formats.
- **The memory device** (`hal/src/rg/mem.c`): a device whose buffers are system memory and which shows nothing.
  It is what the host tests draw on. B3 builds the software device that shows its buffers.
- **Glide's software back end:** not in B2. It is next on the core after GL's, its own step, as the owner answered.

## The decisions it needs (the owner's: questions with this plan)

1. **Scanline spans, not half-space blocks.** The core walks each triangle's edges a row at a time and draws a
   span between them with a routine chosen once per state (flat or smooth, textured or not, depth, blending: a
   few dozen variants made from one template).
   - **For it:** on a 486 or a Pentium II (the CPU floors), spans do the least work per pixel. Each pixel costs
     one add per attribute, with no per-pixel edge tests. Perspective is corrected every 8 or 16 pixels and
     interpolated between (Quake's way), with the exact division at each span's ends.
   - **Against it:** half-space blocks suit SIMD and many cores, but the Pentium MMX and II are not wide enough to
     win back the edge tests at 320x200.
2. **Screen tiles from the start (the owner's 2026-11-09 answer), drawn in order on one core in v1.**
   - **How:** triangles are binned by the tiles they touch (64x64 pixels by default), and then each tile is drawn
     in submission order, its span routines clipped to the tile.
   - **Why it helps one core too:** a 64x64 tile's colour, depth and stencil at 16 bits (24 KB) stay in the Pentium
     II's 512 KB L2 while the tile is drawn.
   - **What it leaves open:** more cores later draw different tiles. Bins flush at a swap, a read, a texture change
     a bin still refers to, or when they are full.
3. **Exactness: OpenGL's rules, checked against OSMesa** (D16) with the conformance tolerances as they are:
   - the top-left fill rule at pixel centres;
   - sub-pixel precision of 4 bits (28.4 fixed point);
   - attributes at pixel centres;
   - texel centres for sampling, and the level of detail from the derivatives.

   Where the core approximates (perspective between the 16-pixel steps, fog per vertex), the tolerances must cover
   it, or the approximation goes.
4. **Depth: 16 bits, and 32 where a program asks** (DGLConfig `depth_bits`). **Stencil: 8 bits** from the start,
   with a separate span loop when the test is off, so programs without stencil pay nothing (B0's review).
5. **Colour: RGB565 and XRGB8888 first, then 8 bits.** The 8-bit form is a fixed 3-3-2 palette with ordered
   dithering. The core draws in its own 8-8-8 inside a span and writes the buffer's format at the span's end.
6. **MMX: compiler intrinsics** (`<mmintrin.h>`, gcc 12 in both builds), chosen at start-up by CPUID, beside plain
   C that the host tests run too. Both paths are compared with OSMesa, and with each other bit for bit where the
   arithmetic is meant to be the same.

## The steps

Each step is a commit that builds every part and passes the host tier. Main stays B1-identical for the Matrox
devices throughout: the software back end is only chosen by `DGL_DEVICE=soft`, or on the memory device.

1. **B2.0, the documents:** this plan, and `backends.md`'s step B2 pointing at it.
2. **B2.1, the frame:**
   - the core's header and an empty pipeline;
   - the memory device;
   - GL's software back end on it, drawing nothing yet;
   - a host build of DOS-GL with it (32-bit Linux, as the rig build);
   - `make soft-conform`, which runs every conformance test there, compares it with OSMesa and lists what fails
     (all of it, to start).
3. **B2.2, triangles:**
   - the edge walk and the top-left rule;
   - flat and smooth colour;
   - depth (16 and 32 bits), scissor and the colour mask;
   - clearing.
   - Plus host unit tests of coverage: a seamless mesh with no pixel missed or drawn twice, and every edge
     orientation.
4. **B2.3, textures:**
   - the core's texture formats and storage;
   - nearest, bilinear and mipmaps, with the level of detail;
   - perspective;
   - the four environments, and the two units (GL_ARB_multitexture's combine as DOS-GL has it).
5. **B2.4, per pixel:** alpha test, blending (every GL 1.1 factor), fog (per vertex and per pixel, linear, exp,
   exp2), stencil (8 bits, its test and operations), and logic ops if the conformance set uses them.
   - **The public part:** `DGLConfig.stencil_bits`, at the structure's end, as B0 settled. A zeroed `DGLConfig`
     still asks for none. `glGet(GL_STENCIL_BITS)` comes from the back end's caps (0 on Matrox).
6. **B2.5, lines and points:** GL's rules for wide and thin lines and points, stipple where DOS-GL offers it.
7. **B2.6, the buffers' formats:** 32 bits and 8 bits (the fixed palette, dithered); conformance at 8, 16 and 32.
8. **B2.7, tiles:** binning and drawing tile by tile, the same pixels as B2.2 to B2.6 drew directly (checked bit
   for bit on the host).
9. **B2.8, MMX:** the span loops that matter (textured, smooth, blended) in MMX, chosen by CPUID; host conformance
   with and without.
10. **B2.9, speed:** frames timed on the host (callgrind's instruction counts with the P6 tables, as Part C's
    model did), then on real CPUs of the floors' class: bench-g400's Pentium II (games at 320x200) and bench C's
    486DX4 (GLOS's screensavers; the floor is a 486DX2), booked with GLOS's session. The P4 bench, B4's tier 3,
    runs the whole matrix later; B2 does not wait for it.

## The checks

- **Host, on every change** (tier 1): all 32 conformance tests through the software back end against OSMesa at
  16 bits from B2.2, and at 8, 16 and 32 bits, with and without MMX, from B2.6 and B2.8. Plus the core's unit
  tests: coverage, the fill rule, texture sampling and blending arithmetic, against small references in the tests.
- **The Matrox devices:** untouched. RetroGPU's merge tier at each merge, and the register CRC subset against
  main's baseline.
- **Loop A:** none in B2 itself. The software renderer reaches the screen in B3, which brings tier 2's smoke on
  86Box's S3 card.

## Where it stands (2026-11-14)

- **Done:** B2.0 to B2.7. `make soft-conform` passes all 34 tests within the manifest's tolerances, at 16, 32 and
  8 bits (`BPP=`), and RetroGPU's host tier (`tools/regress.sh host`) runs all three.
- **The fill rule (decision 3, corrected).** For a pixel centre exactly on a horizontal edge, OSMesa (llvmpipe,
  drawing a window-system framebuffer with y down) counts the polygon's bottom edge, not its top one
  (`bottom_edge_rule`). GL's back end now asks the core for that rule (`SOFT_FILL_BOTTOM_LEFT`). The top-left
  rule stays in the core as an option, for Glide. Left edges count under both. t34's third frame draws such ties
  and matches OSMesa exactly; t15 has 990 fewer differing pixels than under top-left; no frame has more.
- **Lines and points (B2.5)** follow OpenGL's rules as llvmpipe applies them (`lp_setup_line.c`,
  `lp_setup_point.c`), since its frames are the references:
  - **lines:** a parallelogram whose ends move by the diamond-exit test, its width rounded to a whole number
    (halves to even) across the minor axis, its attributes varying along the major axis only, flat shading from
    the second vertex;
  - **points:** the legacy square of the rounded size (halves down), odd sizes about the pixel holding the point
    and even ones about the nearest corner, culled when the centre is outside the view volume.

  DOS-GL has no `glLineStipple`, so there is no stipple. t34 runs on the software renderer only: the Matrox back
  end draws lines as plain quads, without the diamond-exit ends.
- **How close to OSMesa, exactly.** The manifest's comparison allows 24 levels and ignores the reference's edges.
  Counted with no tolerance and no edge mask (after RGB565 quantisation):
  - **identical:** t01, t02, t04, t05, t08, t27, t33, and t34's points and ties frames;
  - **t34's lines:** 21 pixels, one step each (colour rounding along the lines);
  - **the rest:** edge pixels where the core's 1/16 grid and llvmpipe's 1/256 one snap a vertex differently, and
    filtering and blending rounding. Examples: t03 46, t09 69,819 (by at most 9), t12 954, t13 20,675, t17
    63,025 pixels.

  That is the plan's design (4 sub-pixel bits, tolerances as they are). Since B2.7 the core's own frames are the
  reference for what follows: tiles, and later MMX, must draw them bit for bit.
- **Colour depths (B2.6).** The device decides what it draws; `dglInit` no longer refuses all but 16 bits. The
  Matrox devices still draw 16 only, and the memory device draws 8, 16 or 32. `GL_RED_BITS` and the other colour
  queries report the depth (3-3-2, 5-6-5, 8-8-8), and `rg_opened.color_bits` carries it.
  - **32 bits** is XRGB8888 with no destination alpha. It passes as 16 bits does.
  - **8 bits** is the fixed 3-3-2 palette. With GL_DITHER on (GL's default) it gets a 4x4 ordered dither, unbiased,
    so any 4x4 block averages back to the colour within 1/32 of a step (`tests/unit/test_softfmt.c`); with it off,
    each channel rounds to the nearest level.
  - **16 bits stays undithered,** like the references.
  - **The 8-bit comparison:** both frames go through imgcmp's 4x4 box (`_default_soft8`). Two frames get an
    allowance at 8 bits only, each for a limit of the format, with the reasons in the manifest:
    - t09: blending reads back a dithered level and dithers again with the same threshold;
    - t16: checkerboards change colour at the dither's own scale.
  - **imgcmp's box filter** now sums rows and then columns. Its output is identical and it is three times faster,
    which also helps Glide's dithered comparisons.
- **Tiles (B2.7).** With a tile size set (`DGL_SOFT_TILE`, 64 by default, 0 to draw at once):
  - **What is kept:** triangles, lines, points and clears, each with the state in force. The state copy includes
    the textures' descriptions but not their texels, and identical states are shared.
  - **Binning and drawing:** each command goes into the bins of the tiles it touches. At a flush every tile is
    drawn, its commands in order, each with its scissor cut to the tile.
  - **When it flushes:**
    - at the memory device's sync, swap and read, through `rg_softbuf`'s hooks, so the device does not depend on
      the core;
    - when the target changes;
    - when the 1 MB store is full;
    - before GL changes or frees a texture that kept work samples (`dgl_backend.tex_change`, a hook that is NULL
      on the Matrox back end, and `tex_free`), judged by the epoch each texture was last used in.
  - **The arithmetic, made position-independent first:** a span used to step its attributes from its first pixel,
    so a span cut at a tile's edge could round differently. Each pixel's attributes are now the row's base plus
    x steps. That alone moved pixels in the textured tests, where texel boundaries fall exactly on pixel centres
    and nearest sampling goes either way, OSMesa's too. For example: t14 2,002 to 1,365 pixels differing from
    OSMesa, t19 4,382 to 2,904, t23 8,717 to 9,412. All pass, and those frames are the new baseline.
  - **Checks:**
    - `tests/unit/test_softtile.c`: 180 random sequences, each replayed through tiles of 64, 16, 7 and 1 at the
      three formats, leave colour, depth and stencil identical (720 runs). The test fails on a missing tile cut
      and on a span-start dependence, both tried.
    - `make soft-tilecheck` (in the host tier): all 37 conformance frames at 16, 32 and 8 bits through tiles of 64,
      16 and 7 against drawing at once, 333 comparisons, all identical. Without the texture hook 45 differ (t18,
      t19, t29, t31 and t32, which change textures between draws).
- **Found, not changed:** neither back end confines drawing to a viewport smaller than the window. Both clip by a
  guard band and cut only at the window and the scissor, so geometry past the viewport's sides draws outside it,
  where GL would clip it. Games usually draw their 2D over the border afterwards, which hides it. t34 keeps clear
  of it. **The owner's answer (2026-11-14): fix it after B2 merges, in both back ends, as one change** (each
  scissors to the viewport inside the scissor), with the Matrox merge tier and a conformance test of a small
  viewport.

## B2.8's design (2026-11-14)

MMX works on integers, and the core's spans are double precision, so B2.8 comes in three parts:

1. **Fast spans in C, in integers.** One routine per class of state, chosen when a state is set (decision 1's
   template): flat or smooth colour, depth on or off, textured or not, blended or not. Other states (stencil,
   alpha test, two units, fog) use the reference span until profiles say otherwise (B2.9).
   - **Colour:** 16.16 a channel.
   - **Depth:** 16.16 for 16-bit buffers; 32-bit depth stays on the reference span.
   - **Texture coordinates:** s/q and t/q divided exactly at screen columns divisible by 16, linear in 16.16 texels
     between; the level of detail per 16-pixel piece.
   - **Texels:** nearest by masks (power-of-two sizes); bilinear with 8-bit weights. Modulate and blending in
     8-bit integers.
   - **Tiles stay exact:** every pixel's values depend on its position alone, so tiles stay bit-identical.
2. **MMX** versions of the hot routines (smooth, textured, blended), chosen by CPUID, with `DGL_SOFT_MMX=0` to turn
   them off.
3. **The reference span stays** (today's), as `DGL_SOFT_EXACT=1`, for the tests and for diagnosis.

**Checks:**
- `soft-conform` at 8, 16 and 32 bits on the fast spans, within the manifest's tolerances;
- MMX against the C spans, every frame bit for bit (as `soft-tilecheck` does for tiles);
- `soft-tilecheck` on the fast spans.

**The plan's wording changes in one place.** Decision 1 has "the exact division at each span's ends". A span cut
at a tile's edge would then divide at a different place from the whole span, and tiles would no longer be exact.
Dividing at fixed columns keeps tiles exact with the same accuracy (16 pixels between exact points either way).

## Risks

| Risk | What answers it |
|---|---|
| Too slow for the floors | Spans, not blocks; per-state routines; MMX; tiles for the cache; measured from B2.9 on, and the floors are GLOS's per-app minimums, which can move with the owner's say |
| OSMesa's choices differ from the core's where GL allows either (polygon edges, LOD, fog) | The conformance tolerances, as for the Matrox cards; differences outside them looked at one by one |
| The core grows GL-shaped and misfits Glide | Its state is designed from Glide's combiners and fog table as well (Glide's runtime is in this repository), and Glide's back end follows next |
| Tiles cost more than they save on one core | B2.7 is measured against drawing directly; tile size is a setting |
| Host and DOS builds differ in the x87's precision | The host build is 32-bit with x87 maths, as the rig build is |

## Not in B2

- Showing the pixels (VBE, GLOS windows) and the `dglInit` change: B3.
- Tiers 2 and 3 of the tests: B4.
- Glide on the core: its own step after B2.
- More than one core: after GLOS v1 (the owner's answer).
- The ViRGE's GL back end (V4), which falls back to this core for what the chip cannot draw.
