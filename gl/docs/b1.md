# B1: DOS-GL's Matrox code behind the back-end interface, a plan

**Status (2026-11-13): v1, approved by the owner ("Approve, start B1"); under way.** Step B1 of the software renderer's plan
(`docs/backends.md`), on the interface B0 settled (`docs/backend-interface.md`, v2). Built by the DOS-GL session
(the owner, 2026-11-13), on RetroGPU branch `b1`.

## What B1 is

DOS-GL's GL layer (`gl/src/gl`, `gl/src/dgl`) calls the Matrox HAL in about ten files today. B1 puts that code
behind B0's two levels, and **changes nothing that draws**:
- **the device** (`rg_device`, beside the HAL): the card, modes, buffers, showing, video memory, sync, reading,
  teardown;
- **GL's drawing back end** (`dgl_backend`, in `gl/`): clip-space triangles, lines and points, state, clears,
  textures.

Only the Matrox implementations exist after B1. The software ones are B2 and B3, and the ViRGE/DX's device is its
step V3. The point of B1 is that each of those is then new code beside the Matrox code, not edits through it.

**The rule for the whole step: moves and adapters only.** Code moves with `git mv` where a file moves whole (so its
history follows), and otherwise moves as it is, with a function table in front of it. No arithmetic, register value or
order of writes changes. Where code has to change to fit the interface (the colour packing in `glClear`, the
RGB565 read in `glReadPixels`), the change is the same arithmetic in a new place.

## Decisions B0 left to B1

- **Names and folders:**
  - **The device:** the header is `hal/include/rg/device.h`, holding `rg_device` and its structures (`rg_caps`,
    `rg_mode`, `rg_open`, `rg_surface`, `rg_mem`, `rg_stats`, `rg_info`, `rg_cursor`). The list of devices and the
    choice by `DGL_DEVICE` are in `hal/src/rg/device.c`, and the Matrox device in `hal/src/rg/mga.c`. They are
    built into the HAL's DJGPP, host and rig libraries, but not into Glide's Open Watcom build until Glide moves onto
    the device in its own plan.
  - **The Matrox HAL stays where it is** (`hal/src`, `hal/include/mga`). The merge plan's later move to `hal/mga/`
    is not part of B1: it would touch Glide and GLOS for nothing B1 needs.
  - **GL's back end:** `gl/src/backend/backend.h` (`dgl_backend`, `dgl_caps`) and `gl/src/backend/mga/`. That holds
    `emit.c` (moved whole), `tex.c` (`texture.c`'s card half), the hardware texture formats from `texconv.c`, and
    the combiner words from `combine.c`.
- **Video memory is the device's.** `vram.c`, the heap, becomes the Matrox device's `alloc` and `free`, so the
  device owns all of VRAM: the colour and depth buffers it makes at `open`, and the textures the back end asks for.
  This refines the census, which put `vram.c` in the back end. Glide's and GLOS's desktop's VRAM can share it later.
- **No public change in B1.** `dosgl.h` and `DGL_API_VERSION` (0x0104) stay as they are, and every program, port
  and sibling (SDL3 bridge, Fifth Wheel, dgk, DOSBench, Echoes, the game ports) builds unchanged.
  - B0's public additions wait until there is a second back end: `DGLDeviceInfo.backend`, 0x0105 (B3), and
    `DGLConfig.stencil_bits` (B2).
  - `DGL_DEVICE` is read from B1 on: unset or `mga` chooses the Matrox device; any other value logs
    `DGL-DEVICE <name>: not built` and `dglInit` refuses, as it does today on a PC without a Matrox card.
- **GLOS's GPU lock** (`DGL_GPU_ENTER`, `DGL_GPU_QUIET`) becomes the device's `enter` and `quiet`, called where it
  is called today.

## The steps

Each step is one commit that builds every part (DJGPP, host, rig, the ports), passes the host tier, and draws the
same in a short Loop A run: three conformance tests on the G400 and one on the G200, compared byte for byte with
main's images. Only the merge needs the whole set.

1. **B1.0, the documents:** this plan, and `backends.md` with the owner's answers of 2026-11-09 and 2026-11-13. The
   2026-11-09 answers were on GLOS's local branch `backends-v2` and never merged.
2. **B1.1, the two headers and the device list, with no users yet.** A host unit test for the choice by
   `DGL_DEVICE`.
3. **B1.2, the Matrox device** (`hal/src/rg/mga.c`), from the code that does each job today:
   - `probe`, `modes` and `info`: from `device.c`, its card search, the mode list with the Matrox rules (pitches,
     VRAM fits, scaled and zoomed modes), and `dglGetDeviceInfo`'s fields;
   - `open`, `close` and `gamma`: from `dglInit`'s card part (the mapping, VRAM layout, mode set, zoom, the first
     clears, the DAC ramp), `dglShutdown`, and `crash.c`'s teardown;
   - `swap` and `present_front`: from `swap_buffers` (the display start, the scaled present, the retrace wait);
   - `sync`, `alloc` and `free`: `engine_sync`, and the heap from `vram.c`;
   - `read`: `readpix.c`'s RGB565 decoding, giving RGBA8;
   - `crash` and `stats`: the WARP, engine and MMIO trace lines, and `ftrace.c`'s counters.

   The GL layer's `context.c`, `device.c`, `readpix.c`, `snap.c`, `crash.c` and `ftrace.c` then call the device.
4. **B1.3, the GLOS path:**
   - **Into the device's `open_glos`, `swap` and the lock:** `glos.c`'s card half, which is API 2.0's GPU and
     window calls, `mga_mmio`, `mga_fb`, GLOS's VRAM blocks and `engine_resync`.
   - **Stays in the GL layer:** whether GLOS wants the program in a window (`dgl_glos_want`, `DGL_FULLSCREEN`), and
     the window's modes.
5. **B1.4, GL's Matrox back end:**
   - **Moved whole:** `emit.c`, with `git mv`.
   - **Split out of `texture.c`:** its card half, which is residency, uploads (the ILOAD, the VRAM moves, the writes
     in place), the TLUT, the epochs and the white texture. It moves behind `tex_ready`, `tex_sub`, `tex_free` and
     `tex_reset`; `dgl_texture` keeps GL's fields and gains `void *be`.
   - **Also moved:** the hardware formats from `texconv.c`, and the combiner's words from `combine.c`.
   - **From `caps` instead of the `mga` record:** `get.c` and `ext.c`.
   - **Into the back end's `clear`:** the RGB565 packing in `glClear`.
6. **B1.5, the checks** (below), then the merge.

## The checks

- **No Matrox headers in the GL layer:** a grep of `gl/src/gl` and `gl/src/dgl` for `mga/` finds only the platform
  headers (`sys.h`, `fp.h`, `prof.h`, `serial.h`, `types.h`). It runs in the host tier from B1.4 on, so nothing
  creeps back.
- **The same register writes:**
  - **What is recorded:** the HAL's MMIO trace hook (`MGA_TRACE_MMIO`) gains a running CRC of every register write,
    and of every WARP vertex buffer's contents as it is handed to the engine. Pointer writes, whose values depend on
    how far the engine has got, are left out.
  - **The comparison:** one CRC for each conformance test on the G200, G400 and G450, for main and for `b1`, equal
    for every test. This is stronger than pixels, because 86Box draws some register differences identically
    (`docs/emulated-g200.md`), but the silicon might not.
- **The same pixels:** every conformance test on the three cards, compared byte for byte with main's images rather
  than within the conformance tolerances. Also the games' frames: ClassiCube, GLQuake and Quake 2 (the merge tier),
  Half-Life (`tools/halflife/cards.sh`), and the SDL examples.
- **The whole regression:** RetroGPU's merge tier on devserver.
- **GLOS:** from a GLOS checkout built against `b1`, the gpu, glwin, sdlwin, games, display, win, desk and api
  suites. GLOS's session runs full gates on devserver from one checkout there, so the run is agreed with it first,
  or it runs it.
- **Speed:** DOSBench's DOS-GL runs on bench-g400, main against `b1`, within noise. This is agreed with GLOS's
  session, which uses that bench too. On 86Box, the hot path gains no indirection: the sink is already called
  through pointers, and `emit.c`'s inner functions stay static inside the back end.
- **Builds of the siblings:** Fifth Wheel, dgk, DOSBench and Echoes build against `b1` unchanged (no public change).

## Risks

| Risk | What answers it |
|---|---|
| A move changes the order of register writes (a sync or a reset ends up elsewhere) | The register CRC per test, which pixels alone would miss |
| The device's table grows around GL's needs and misfits Glide, GLOS's desktop or a second card | B0 drew it from all three users. The ViRGE/DX's device (V3) is a second implementation soon after, and the TNT2's plan checks again |
| `texture.c`'s split leaves GL code reading the card's fields | Those fields go behind `be`, so a missed reader fails to compile |
| A long-lived branch collides with others' work in `gl/` | The GLOS session has nothing in `gl/` planned (2026-11-13). Rebase onto main at each step and check main before each merge |
| B1 takes the GLOS gate's devserver checkout | Agreed with GLOS's session each time |

## After B1

`docs/backends.md`'s order is B2 (the software renderer) next. The ViRGE/DX's device (`docs/virge.md` V3) could
come straight after B1 instead: it is small, because the ViRGE's modes, 2D, cursor and start are already in
`libvirge.a`, and it is the first check that `rg_device` fits a second card before B2 builds on it. **The owner's
answer (2026-11-13): V3 first, then B2.** The ViRGE's GL back end (V4) still waits for B2, for what the chip cannot
draw.
